# CodeCanopy Claude adapter

This adapter maps a node explicitly assigned `claude` to the locally installed Claude CLI. The runtime checks `claude` is available, then invokes headless JSON mode with `--safe-mode`, `--strict-mcp-config`, `--no-session-persistence`, browser and slash commands disabled, and WebFetch, WebSearch, and MCP tools denied. Safe mode disables repository and user customizations while preserving normal authentication. Read-only nodes receive only Read, Grep, and Glob; writing nodes add Edit and Write inside a verified worktree. Bash and agent tools are unavailable, so the root process runs checks. The adapter uses `--permission-mode plan` for read-only nodes or `--permission-mode acceptEdits` only for writing nodes, plus `--max-turns 8`. The trust-boundary prompt is an argument, not shell input.

Claude model, authentication, permissions, concurrency, and worktree policy remain Claude/host concerns. CodeCanopy does not claim that Codex roles, model preferences, limits, approval behavior, or manifests are portable to Claude. A writing node still receives a caller-created detached Git worktree and must pass the provider-neutral acceptance barrier.

The bundled `auto` selectors resolve to Claude provider aliases at new-run start: `best` for lead, `sonnet` for expert and reviewer, and `haiku` for worker. The alias catalog hash is frozen through execution and resume. CodeCanopy does not infer an exact backing ID from an alias; it records one only when the completed JSON output has unambiguous `modelUsage` evidence. A malformed or incomplete catalog blocks dispatch, and previews are not intentionally selected.

If `claude` is unavailable, the adapter fails closed. It may run Codex only when the caller authorized that exact transition before dispatch and Codex is available. The result records `requested_provider: claude`, `provider: codex`, `fallback_used: true`, and the reason. The subprocess environment is allowlisted and never transfers Codex credentials to Claude or Claude credentials to Codex. A successful headless run proves only that local invocation completed; it is not a quality, production, or cross-provider-equivalence claim.
