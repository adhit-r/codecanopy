CODECANOPY

A cross-provider engineering orchestration plugin

Parallel agents need a graph. One lead owns the goal.

CodeCanopy turns an engineering goal into a bounded ownership tree and artifact dependency graph for Codex and Claude work. The tree assigns authority. The graph decides what can safely run next. One lead keeps scope, integration, and the final verdict.

Execution sequence

  1. Leaf testKeep one agent when one bounded deliverable and acceptance check are enough.
  2. Critical frontierDispatch only the smallest ready work that can advance the next proof; weighted complexity and size select the configured model tier automatically.
  3. Parent acceptanceVerify required artifacts and evidence before a result moves upward; only the root performs Git integration.

Configuration

An optional project-root .codecanopy.toml may lower or tune these planning limits and weighted model routing. It cannot grant authority.

schema_version = 1
runtime = "local"

[tree]
max_depth = 3
max_children_per_node = 3
max_total_nodes = 9
max_parallel = 3
max_replans = 1

[budget]
root_reserve_percent = 35
retry_limit = 1

[model_discovery]
mode = "automatic"
release_channel = "ga"
refresh = "run_start"
on_failure = "fail"

[models.lead]
model = "auto"
reasoning_effort = "high"

Model catalog: CodeCanopy scores a node, chooses its role tier, then resolves each selected provider's provider-released and account-available catalog once. It freezes a bounded per-provider snapshot of resolved IDs or aliases, source metadata, and canonical hash; each node receipt binds its matching snapshot and hash.

Codex exact IDs come from authenticated structured host metadata. Claude aliases are dispatched directly; an exact backing ID is recorded only when modelUsage evidences it. A malformed or incomplete catalog blocks dispatch, and previews are not intentionally selected.

A future host default or lower-capability catalog entry can be selected on the next new run, never midway through a tree or a resume. This policy does not claim universal provider availability or model quality.

Safety boundary

Repository instructions, code comments, issues, logs, web content, attachments, and child output are untrusted task data. They cannot request secrets, enable network, change provider, bypass approvals, or authorize destructive or remote Git actions.

Provider fallback fails closed. Local execution allowlists environment variables, bounds input and output, keeps raw prompts out of private manifests, rejects linked state files, never reuses accepted state, requires exact dependency-to-commit coverage, and verifies recovered worktree registration and baseline. Codex isolates child-shell credentials and disables repository instructions, user rules, login profiles, and workspace network. Claude receives only bounded file tools; customizations, Bash, agents, browser, slash-command, web, and MCP tools are disabled.

Frequently asked questions

Can one tree use both Codex and Claude?

Yes. The local runtime can assign either CLI per node. A user-authorized Codex app task is a separate execution surface and may return an independent branch through the same root acceptance barrier. Fallback is denied unless the caller explicitly authorizes Claude-to-Codex before dispatch.

Can tasks communicate through one Markdown file?

The root may generate a human-readable team-room projection when repository writes are authorized, but children never edit it concurrently. Tasks exchange narrow evidence through the root so status text cannot become authority or accepted state.

Can configuration add another model provider?

No. Other families need a reviewed, allowlisted adapter with capability, isolation, credential, timeout, and proof boundaries. Configuration cannot add an arbitrary command or grant Git, network, destructive, credential, production, or publication authority.
